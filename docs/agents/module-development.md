# 开发约定

接手、执行或派发产品分区或共享技术底座任务时读本页；当前进度、工作树和权限读[项目状态](../plans/run-state.md)。用户本次指令及已生效授权优先，旧任务安排不自动延续。

## 接手与完成

1. **确认需求与现场。** 用户交代任务或指定 Issue 后，先确认需求、负责范围与完成结果；需求含糊时在原会话或原 Issue 线程追问，需求明确后才实施。技术事实、依赖及验证方法由 agent 自行调查，不交用户代查。只收到“负责某模块”时先接手说明，不自行挑选需求或领取其他 Issue。核对指定 worktree、Git 分支/HEAD、暂存区、未提交及未跟踪源码，明确须保留的成果。
2. **按任务读取。** 从[功能索引](../README.md#功能规格)进入本产品分区规格，并按根[项目入口](../../AGENTS.md#项目入口)核对本任务的必读条件；变更共享语义再读其契约，涉及 UI 再读[设计输入](../design-system/README.md)。按索引定位相关章节，已读且未变化的内容复用；长日志先取摘要和失败片段，避免批量输出整篇文档或日志后因截断重读。产品范围由规格和用户要求决定。产品分区沿[范围](../PRODUCT_SCOPE.md#产品分区)的八项划分；注册业务模块只是其中一部分。公共能力按[共享技术底座](../README.md#共享技术底座)进入，阅读相邻分区或公共契约不授予其写权。
3. **明确交付条件。** 用用户实际入口、操作和最终成果描述完成条件，固定输入、修改范围及提交/保留 diff 方式；选择验证前必读[CI 与本地验证](github-workflow.md#ci-与本地验证)，按当前角色确定验证范围。沿已有任务包执行，普通开发无需用户填模板。用户无需阅读代码或管理派工来确认基本可用。缺少影响行动的关键条件才澄清，常规实现选择自主完成。
4. **核对完整目标再交付。** 逐项对照用户原始目标、后续有效调整与完成条件，验证受影响的真实使用路径及必要回归，核对已集成和运行版本，更新相关事实。批次通过只完成该批；范围内必要缺口继续推进或明确受阻，不能转为范围外发现后关闭任务。按[回执](#回执)区分完成、失败、未验和剩余事项，最后按[集成后的清理](#集成后的清理)收尾。

## 当前任务记录

跨阶段、跨 session 或存在多条依赖的长程任务，在 `docs/plans/` 保留一份入库的当前记录；已有记录继续维护，小改可直接执行并回执，不强制建计划。任务负责人维护本记录，总控维护全局[运行台账](../plans/run-state.md)中的任务入口、工作现场和授权；两者用链接分工，事实只更新所属位置。

记录须足够让未读旧聊天的新 agent 独立接续：完整目标及需求依据、授权与写入/运行边界、依赖和固定输入、当前候选与状态、未决需求及阻塞、完成证据、下一步与剩余完成条件。可直接链接台账或正式 Issue 的唯一事实，不复制第二套状态；必要输入和接手信息不能只存聊天或忽略目录。格式按任务需要组织。

阶段结束、目标或授权变化、依赖/阻塞改变、暂停或交接前，覆盖更新当前事实和证据入口，保留尚未完成的完整目标。接手者先读台账及其指向的任务记录，核对实际 Git 现场与证据，再续做下一步；有冲突先查明，不能沿旧回执猜测完成。关闭记录前按[接手与完成](#接手与完成)核对整体结果，分批集成不改变原目标。

## 范围与发现

当前授权范围内影响完成条件的问题由本任务解决或明确受阻。检查中发现改法明确、影响局部的小问题可以顺手修复，最终说明，包括明显 UI、lint、测试失败和不稳定问题；跨文件或不属于当前模块不自动要求用户许可。并行任务仍保持唯一写者，涉及其他执行者负责的文件或公共文件时先由总控协调归属。

影响较大且需要用户决定方向或取舍的发现记根 [buffer](../../buffer.md)，按其收录规则写清裁决依据；已授权范围内的必要工作不能转入 buffer 逃避完成。其他超出授权的问题交总控协调范围，记录本身不扩大授权。已获准但暂缓的任务留在其任务记录或运行台账，buffer 不承载第二套任务进度。

## 实现原则

实现与 Standards 审查依据[代码标准](../code-standards.md)，修改代码前读 [Lessons](../../LESSONS.md)。产品行为从功能规格进入；修改子系统先读[运行参考](../subsystems/README.md)并核对实际源码。阅读相邻模块或公共契约不授予写权。

## 开发与验证

按[验证入口](../acceptance/README.md)选择与本次使用结果匹配的反馈，按[CI 分工](github-workflow.md#ci-与本地验证)区分本地定点、云端回归和目标环境专项。修 bug 的 E2E 复现、断言与隔离判据以代码标准为准，不因每次编辑、提交或创建 PR 重跑完整回归。

## 仓库维护

用户要求仓库维护、阶段整理或集成后的整体核查时，先按[接手与完成](#接手与完成)固定授权范围、基线和候选，再按下表展开；日常交付无需逐项全库检查。用户未指定细项时，从仓库入口、现存现场及最近集成改动的依赖进入，抽查不能证明全库健康。

| 检查面 | 所需事实 |
| --- | --- |
| 成果与现场 | 未提交及未集成成果归属，已完成现场按[清理流程](#集成后的清理)是否仍有保留理由 |
| 文档与状态 | 唯一权威事实与实现一致，入链、锚点、消费者及固定引用有效 |
| 输入与可移植性 | 可从检出、模板及明确外部获取方法重建，无个人路径或本机独有对象前置 |
| 模块职责 | 运行参考对应实际调用与数据归属，公共端口未绕过，替代实现无失效残留 |
| 验证链路 | 输入和断言保护当前行为，隔离及已运行证据覆盖所声明结果 |
| 体验与运行 | 实例运行本次候选，受影响真实入口可用，测试与体验数据隔离 |

每项区分已核对、实际发现、不适用及未验。沿线索核对实际消费者，文本搜索仅作线索，动态加载内容不能只因未搜到引用而删除。按[范围与发现](#范围与发现)处理问题；目录重排或重构须对应实际缺口及授权。准备路径或依赖变化按代码标准实际重建，文档改动只核对受影响事实、引用与阅读路径；其余验证沿[开发与验证](#开发与验证)分工。当前事实更新所属权威位置，任务状态按[当前任务记录](#当前任务记录)维护，按[接手与完成](#接手与完成)收尾；零改动也须说明核对依据。

## Git 与运行现场

新一轮开发按[GitHub 协作与发布](github-workflow.md)及[当前授权](../plans/run-state.md#工作现场与授权)确认负责 session、分支起点和现场归属。用户明确指定工作方式时照做；总控先按[任务与 PR](github-workflow.md#任务与-pr)确定路径，再在该路径内安排工作现场：

- 并行写代码、需要独立运行环境或保留另一条工作现场时，创建独立 worktree。
- 串行小修复只创建短期任务分支并复用目录；切分支前核对未提交成果和运行中的服务。目录承载体验服务或其他未提交工作时，由总控安排可安全操作的目录或串行时机。
- 同一任务返工复用原现场，只读审查无需新建 worktree；完成集成验证后按[清理规则](#集成后的清理)收尾。未集成源码、固定输入及有效证据须保留，记录可接续的版本和位置。

日常任务从 `preview/integration` 的固定提交创建短期分支；直接合入或 worktree PR 集成的分流、禁用 PR 的范围及推送规则统一见[任务与 PR](github-workflow.md#任务与-pr)。CI、版本准备及 main 发布沿同页执行，候选和证据留回执或集成 PR。

公共文件同一阶段只有一个写者。总控负责集成冲突，业务 session 不互相派活或扩大任务。Git 操作按本次授权执行，提交不自动添加 agent co-author；未提交及未跟踪源码均属成果，不能覆盖或把已集成增量重复应用。

preview 直接运行集成源码，获准改动会进入用户体验；模块在隔离实例自测。工具、环境和需要手动重启的变更交总控协调，入口见[运行指南](../SETUP.md)。测试数据的处置范围按项目状态；代码、固定输入、证据与私有配置按用途保护，不能因旧数据可丢弃而降低新保存/历史/导出的正确性。

文档事实发生变化时，按[文档维护](../code-standards.md#文档维护)同步所属权威位置。沟通使用中文、普通短横线；问句默认信息请求，明确执行指令优先；暂停、先回答等要求限定当前动作。

### 集成后的清理

总控在集成验证通过的同一轮交付前完成以下步骤，清理属于完成条件，不延后到下一轮开发：

1. **确认成果已保留。** 核对任务提交已进入集成基线，工作树没有待保留的未提交或未跟踪成果，相关执行者与临时服务已停止使用现场。经 cherry-pick 或 squash 集成时核对补丁、冲突处理及最终内容；不能只凭分支名称或 `git branch --merged` 判断。删除前确认入库文件不依赖待删分支或其独有提交。
2. **移除已完成现场。** 删除本轮已完成任务的临时 worktree 和本地任务分支；只有分支、没有独立 worktree 的任务也须清理分支。保留 main、当前授权的集成分支与持续使用的工作树。临时产物按验证指南清理，固定输入和有效证据按用途保留；远端操作仍按本次授权执行。
3. **核对剩余项。** 用 `git branch --list`、`git worktree list` 和保留工作树的 `git status` 确认实际结果，并在回执中报告。因未集成、验证失败或继续使用而保留的任务现场，在项目状态中注明归属、保留原因、下一动作和清理触发条件，交付时列为未完成收尾项。

## 编排

仅总控在派发、恢复或接收任务时展开本节；模块执行者沿本次任务即可。依赖与权限允许时并行推进，一条工作线等待用户不阻塞其他已授权工作；大规模 subagent 工作流按根 AGENTS 先取得明确批准。

派发时从用户原始委托及有效调整核对[当前任务记录](#当前任务记录)的完整目标，再拆成可在实际入口使用的批次，依赖满足即集成并验证，及时暴露跨模块问题。收到回执后，总控核对候选和证据，继续安排缺口修复、获准集成与收尾；作者提交或单批通过不是总目标完成。

自主推进至约定结果，只有缺少无法自行取得的关键输入、用户专属操作或授权时才暂停受阻部分，并说明已完成什么、具体缺什么和可继续的工作。已授权的下一步直接执行；讨论、明确暂停及 main/远端等权限边界继续有效。交付前由 agent 准备可用入口和必要示例，完成技术回归，用户主要判断实际效果与偏好。

方案讨论先明确用户要的结果与硬约束，把提出的实现路径作为待检验假设。区分已证实、推断与待验证，关键不确定性先做能改变决策的最小验证；同一输入和判据比较方案，给出明确推荐与取舍。证据足够后推进已授权实现，不把讨论当实现授权，也不把技术判断推回用户。工程取舍按代码标准执行。

任务只携带目标、固定输入、必读资料、写入/运行边界、完成条件与回执位置。必读资料包含[CI 与本地验证](github-workflow.md#ci-与本地验证)；完成条件写清本地定点验证、交 CI 的回归和 CI 未覆盖的必要专项，附可复用的候选与证据入口。输入用 commit + path，未提交或外部材料按需记录摘要；共同文件标明唯一写者、消费者和兼容条件。具体 session、模型/effort、版本及阶段记录留本次任务目录，不积累到长期规则。

独立核验按完整改动目的或大阶段触发：作者定点自验通过、候选版本固定后，集中安排一次独立审查与必要验收。阶段集成后只补跨模块新组合与尚缺证据的范围；返工复验修复项及其影响，不按每次编辑、提交或测试另开一轮。

固定代码 diff 审查按 code-review skill 的触发条件执行，由两个独立 subagent 分别执行 Standards / Spec；先核对基线和修改范围，`<fixed-point>...HEAD` 不包含未提交成果。候选变化时补审新增及受影响部分，包括冲突处理和集成差异。同一固定候选的完整 Standards/Spec 独立审查可直接满足开发 PR review，复用条件与 Release PR 职责见[审查分工](github-workflow.md#审查分工)。普通文档整理做引用、事实和阅读路径自检，不追加重复审查。

同一问题在首次候选与两次有新证据的修复后仍验证失败时，按表中困难接手配置接手一次。每轮保留候选、失败证据与据此作出的修正；失败按三轮完整候选验证计算，原始 bug 复现、开发中的单次命令报错和重复执行同一命令不单独计轮次。环境问题先补运行条件，输入或契约问题交责任方。

## 回执

一份回执足以接续即可：目标及实际 session/model/effort、输入与产物版本、修改范围、实际验证和证据、剩余事项与下一步。验证说明区分本地已验、已有 CI 结果及待 CI/专项验证，交 CI 的项目在运行通过前仍属未验。记录运行环境和身份；审查补固定 diff 及结果。明确已实现、已集成、已验证的范围，区分通过、失败、跳过和未验。

完整目的交付时按 [Lessons 维护规则](../../LESSONS.md#维护规则)核对本轮有无可沉淀教训；没有则不修改。成功后清理临时材料；未完成时保留现场和可接续回执。固定样本与用户成果按用途保留。新会话沿[当前任务记录](#当前任务记录)接续，回执用于提供证据，不替代当前记录。

### 项目进度汇报

用户要求汇报整体项目进度时，使用下列固定格式，从[项目状态](../plans/run-state.md)读取当前事实；本节只保存格式，不保存进度副本。

- 主表按模板顺序列全八个产品分区，即使没有剩余项也保留该行。实现任务和验收事项填入所属分区；共享技术底座单列，数据管理与恢复保留固定行，其他底座按当前事项增行。
- MVP 两列只写剩余实现与剩余验收，不重复已完成成果、通过数量和执行过程。没有已登记剩余项写“无”；信息不足写“待核对”。暂停或缺条件的具体事项标“〔暂缓〕”或“〔阻塞：所缺条件〕”，仍保留原要求。
- 可选增强只列已有候选或明确暂缓的增强，未选定写“暂无已选定项”；用户明确纳入 MVP 后才移入必需工作列。
- 每格用短语说明具体缺口。跨模块综合验收放主表后的独立表，只列剩余事项与当前安排；无剩余时写“无”。最后给一条下一步建议，指明当前可推进的工作或需用户决定的条件。
