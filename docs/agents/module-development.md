# 模块开发约定

负责或接手一个业务模块时先读本页。这里维护各模块共同遵守的长期原则与工作方法；当前任务、工作树、暂停状态和数据处置读[运行台账](../plans/run-state.md)。用户本次指令和已生效的授权优先，旧 session 的一次性操作安排不自动延续。

## 接手流程

1. **确认职责与现场。** 从用户指令和运行台账确定负责模块、当前目标、允许执行的阶段及指定 worktree。核对实际目录、分支、HEAD、暂存区、未提交 diff 和未跟踪源码。完成条件是能说清本轮改什么、在哪里改、哪些现有成果须保留；不能仅凭分支名推断职责或把目录干净当作没有待接手成果。
2. **读取本模块资料。** 按下表进入规格，结合 README 和相关代码确认实际能力、已知缺口及验证入口。规格决定目标，旧实现与原型不能扩大范围。改变共享语义时再读规格指向的契约；涉及 UI 时读[设计与验证规则](../rules/design-and-verification.md)。无需通读其他模块或依赖旧会话记忆。
3. **对齐本轮交付。** 明确用户可观察的结果、涉及文件、必要验证，以及提交或保留 diff、实例操作等已有要求。有任务包时沿用其中固定输入；直接收到开发指令时，从现有上下文补齐这些信息，不强求用户填写模板。缺少影响行动的关键信息才澄清，已获授权的范围内自主推进。
4. **按当前阶段行动。** 只收到“你负责某模块”时，完成接手并简要说明职责与现状，不据此自行挑选新功能。已有明确目标则继续执行；“先判断”“先回答、不动工”和暂停通知限定当下动作，不因读完文档就自动恢复开发。

## 实现与产品取舍

- 优先复用成熟库、开源项目及项目既有能力，再做必要适配。尤其是文档解析、阅读器、数学渲染等已有成熟实现的领域，先核对可复用方案能否满足需求；自建必须有具体能力缺口作为依据。
- 以正确、简单、稳健、长期可维护为主要取舍，不以开发成本为主要理由降低质量。坚持单用户产品的实际需要，采用高内聚、低耦合的直接实现；一次性操作先走最简单的完整路径，具体阻塞出现后才增加机制。
- “尽量补齐”“能改到多少算多少”允许分阶段交付。成熟方案仍无法可靠完成的部分，保留明确能力边界和原因；已交付能力必须可用，不能靠降低断言、伪造数据或退化原功能换取完成。
- 保持已经确认的 UI/UX 风格，新增交互与既有组件、浮层、字号、图标和动效协调。让用户无需教程就能理解用途，随任务逐步展示操作。参考模块用于学习交互，不授予修改该模块的权限；具体规则只在[设计与验证规则](../rules/design-and-verification.md)维护。
- 主动发现并处理本模块内明显的视觉、交互、lint、测试失败和不稳定问题，同时回归受影响的原有能力。跨模块或共享文件的问题交总控安排唯一写者，避免借顺手修复扩大范围。

## 开发与验证

1. **先理解真实路径。** 修 bug 先按贴近最终用户的 E2E 场景复现，保留触发条件、实际结果和失败证据，再定位原因。实现功能时先明确正常路径、失败恢复及受影响的既有行为；只查到一段代码或看到几个用例通过不能证明问题已解决。
2. **在隔离环境实现。** 依[运行指南](../SETUP.md#新的隔离环境)使用独立端口、数据库、文件目录和构建产物。确认实际代码、工具与产物一致；具体工具路径由运行配置维护，不从旧 transcript 复制失效路径。
3. **验证用户结果。** 按功能规格选择真实浏览器、HTTP/数据库集成和真实文件输出检查。保存后刷新或重开、来源变化后的引用、历史恢复、跨模块往返等只在本轮涉及的路径验证。生成 Word/PDF、演示包等成果时实际打开并核对，文件存在或响应成功不足以证明可用。
4. **复核体验与回归。** 查看真实截图、焦点、溢出、裁切和操作可达性，覆盖受影响的主题与尺寸。保住原先可用的解析、保存、草稿、返回及输出行为；失败先区分产品、环境、输入和脚本，取得证据再修。UI 禁止单元测试；其他模块的单元测试仅在确有必要时使用，资源库遵守上表更严格的要求。验证方法与证据等级见[验证入口](../acceptance/README.md)。

## 协作、Git 与运行现场

- 每个业务 session 使用总控指定的单个 worktree，后续改进和返工继续复用；工作树尚未分配时先确认归属，不自行增开。preview 是集成树，当前分工、共享文件写权和集成安排沿[执行约定](../plans/execution-protocol.md#orchestration)。跨模块阻塞向总控报告具体需求与影响，各业务 session 不互相派活或自行扩展任务。
- Git 动作遵守本轮要求。“先提交上一轮，再保留新 diff”应完整保留轮次边界；未跟踪源码也是成果。提交、合并、push 和实例更新分别按已有授权执行，不能把过去一轮的授权自动扩大到新一轮。分支和合 main 规则见根 AGENTS；提交遵循 Conventional Commits，不自动添加 agent co-author。
- 用户体验服务直接运行 preview 当前源码，获准合入或修改 preview 后自动生效；业务 worktree 保留自己的隔离实例完成自测。交付时核实运行进程和工具确实对应本次代码；依赖、配置及需要人工重启的变更交总控协调，维护入口见[运行指南](../SETUP.md#已有本机实例)。
- 尊重用户已打开的浏览器与登录现场。按当前工具能力使用既有连接或隔离测试浏览器，避免反复开默认浏览器、重连或触发授权弹窗。实际操作与验证路径须能复现。
- 数据处置以运行台账和用户最新要求为准。现有测试数据可丢弃的安排不降低新版本保存、历史、引用和导出的正确性，也不涵盖代码、固定输入、工具及运行配置。清理前辨认用途；完成后清理无用临时材料，未完成时保留现场与进展。

## 文档、沟通与交付

代码与相关文档属于同一交付：功能行为、能力边界和验证入口更新到本模块规格；共享语义更新契约；可复用 UI/UX 规则写入设计与验证规则；重要产品或部署变化同步 README。按 `writing-for-agents` 只维护当前准确内容，过程证据留本次产物目录。不手工修改 CHANGELOG 或标为自动生成的文件，根 AGENTS 及受保护文档遵守其维护边界。

用中文简明说明成果、缺口、原因和下一步，不使用英文长破折号。以问句结束的消息默认按信息请求处理，除非其中明确要求执行。已有范围内的常规实现细节自行判断；新增范围或真实权限缺口才向用户澄清。等待其他 session 使用主动回执，不反复轮询。大规模 subagent 工作流须先解释取舍并取得用户明确批准。

完成时按[执行约定的回执](../plans/execution-protocol.md#回执)说明修改范围、版本或未提交路径、实际验证和证据、未完成项与下一步。结论必须区分已通过、未验证、跳过和已知缺口，区分作者自验、独立验收与真人反馈；“已知清单完成”不等于整个模块零缺陷。
