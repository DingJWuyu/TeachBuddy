# 仓库维护流程

用户要求仓库维护、阶段整理或集成后的整体核查时读本页；日常交付按[开发约定](module-development.md#接手与完成)收尾。本页组织检查步骤，工程判据在[代码标准](../code-standards.md)，Git/CI 分工在[GitHub 协作](github-workflow.md)。

## 1. 确认范围与现场

按[接手流程](module-development.md#接手与完成)核对当前授权、Git 分支/HEAD、未提交成果及使用中的实例。固定任务目标、检查基线、候选和未提交差异，明确保留范围后开始。用户未指定细项时核对仓库入口与现存开发现场，再深入最近集成的改动及依赖；抽查不能证明全库无问题。

## 2. 检查实际问题

从[文档入口](../README.md)按任务进入规格、契约、运行参考与验证入口，沿线索追实际调用、数据读取和源码。检查面与所需事实如下：

| 检查面 | 完成核对所需事实 |
| --- | --- |
| 成果与现场 | 未提交及未集成成果归属，已完成任务现场是否仍有保留理由；按[清理流程](module-development.md#集成后的清理)判断 |
| 文档与状态 | 唯一行为/契约/运行入口与实际一致；源码链接、锚点、消费者和固定引用有效 |
| 输入与可移植性 | 从检出、模板及明确外部获取方法重建；无临时目录、个人路径或本机独有 Git 对象前置 |
| 模块职责 | 运行参考对应真实执行路径，数据归属与公共端口未绕过，替代实现无无效残留 |
| 验证链路 | 输入和判据符合当前规格，隔离、有效断言和已运行证据覆盖所声明结果 |
| 体验与运行 | 实例确实运行本次候选，受影响真实入口可用，测试与体验数据隔离 |

每项写明已核对、实际发现、不适用或未验。文本搜索是线索，不是使用关系结论；动态加载文件不能只因未搜到引用而删除。问题记录具体定位、依据与影响，不将抽象偏好当缺陷。

## 3. 按发现处理

范围内已授权且证据明确的问题直接修复，先保护有效成果与用户行为。业务 bug 按代码标准先走真实入口复现；新增能力、目录重排或全库重构不属于固定维护步骤，必须对应当前问题及授权。

暂缓事项沿[运行台账](../plans/run-state.md)执行；范围外发现记录责任与下一动作。必须用户决定的条件先准备具体可审阅结果，同时继续独立工作；本轮普通发现不自动变成永久规范。已证实的重复失误按 [Lessons](../../LESSONS.md#维护规则)沉淀。

## 4. 验证并同步

文档只做受影响事实、引用和阅读路径核对；代码做本地定点反馈，完整回归交 CI，集中审查沿[审查分工](github-workflow.md#审查分工)。复用未变化范围已有证据，不因维护或 push 重验全部。

准备方式、路径或依赖改变时按代码标准在独立检出中实际重建；完整历史或旧缓存可能掩盖本机依赖，验证环境据具体问题隔离。缺输入、工具或硬件时明确未验边界。

事实改变同步所属权威位置，当前缺陷和下一步更新运行台账；执行过程与证据按[产物规则](../acceptance/README.md#隔离与产物)保存，不为每次维护新增永久报告。事实未变无需更新状态副本。

## 5. 收尾与交付

按[集成后的清理](module-development.md#集成后的清理)确认成果保留并处理现场，再按[回执](module-development.md#回执)交付。范围内必要修复和验证通过、事实一致、现场清理完成或有明确保留原因后才报告完成。受阻项与下一动作分别列明；零改动也说明核对依据，维护未发现问题不等于整个产品完成验收。
