# 仓库维护流程

用户要求执行仓库维护、阶段整理或集成后的整体核查时，按本页执行。目标是补齐交付收尾、发现并修复现行规则的违反项，使下一轮开发能从清楚、可验证的现场开始。日常交付仍按[开发约定](module-development.md#接手与完成)及时收尾，不积累到下一次维护。

本页只组织执行步骤。规则以根 [AGENTS.md](../../AGENTS.md)、开发约定及按需展开的权威文档为准；本次用户指令优先。

## 1. 确认范围与现场

先读[工作现场与授权](../plans/run-state.md#工作现场与授权)，按[接手流程](module-development.md#接手与完成)核对实际分支、HEAD、工作树、未提交成果和仍在使用的实例。修改前确认哪些成果必须保留、哪些动作已有授权；在授权的基线上建立本次修改现场。

用户指定范围时按其范围执行。未指定时，核对仓库入口与全部现存开发现场，再深入最近集成的改动及其依赖；发现问题线索时继续追到实际来源。用简短说明记录检查基线（如本轮集成前的提交）、候选提交及未提交差异、检查边界和排除项，不能用抽查结果声称全库已无问题。

## 2. 检查实际问题

先核对下表各项是否适用，再读取对应规则和受影响文件。搜索命中只作为线索，以实际调用、文件读取、Git 差异和运行结果判断；动态加载的文件不能仅因文本搜索不到引用就删除。

| 检查面 | 要取得的事实 | 何时读什么 |
| --- | --- | --- |
| 成果与开发现场 | 未提交、未集成成果及使用者是否明确；候选是否包含预期成果；已完成分支、worktree、临时实例是否仍有保留理由 | 判断集成和删除条件时读[Git 与运行现场](module-development.md#git-与运行现场) |
| 文档与状态 | 入口能否找到唯一、准确的范围、行为和当前状态；改动是否同步；移动或删除后入链及锚点是否有效 | 从[文档入口](../README.md)进入，只展开相关权威页；整理时读[文档维护边界](../../AGENTS.md#文档维护边界) |
| 输入与可移植性 | 受检入口及间接依赖能否从检出、配置模板或明确的外部获取步骤重建；代码或测试是否把文档、临时目录、个人路径或旧 Git 对象当作输入 | 有路径、依赖或准备方式线索时读[项目约定](../../AGENTS.md#项目约定)和[运行指南](../SETUP.md)，区分合法的本机配置与隐含前置 |
| 模块职责 | 改动是否增加重复的权威目录、绕过公共端口、留下已替代且无消费者的实现 | 涉及装配、跨模块访问或公共职责时读[代码结构](../SETUP.md#代码结构)与[模块边界决议](../adr/0001-use-a-single-static-module-catalog.md) |
| 验证链路 | 测试入口、固定输入和预期是否符合当前规格；隔离、有效断言及证据是否完整；失败和跳过各是什么原因 | 有行为或测试变化时读[验证指南](../acceptance/README.md)，再进入相关功能页及场景 |
| 体验与运行入口 | 文档指向的服务是否运行预期源码或构建；开发测试是否使用独立数据和产物；入口变更后是否实际生效 | 维护实例或启动方式时读[已有实例](../SETUP.md#已有本机实例)与[隔离环境](../SETUP.md#新的隔离环境) |

每项形成“已核对、发现问题、不适用或未验证”的明确结论。发现问题时保留定位、依据和影响；不能只写“架构不够好”或“需要继续整理”。

## 3. 按发现处理

对范围内、已有授权且证据明确的问题直接修复。先保留有效成果和行为，再修正冲突、失效引用、隐含依赖、重复职责或验证缺口。业务失败按[开发与验证](module-development.md#开发与验证)先复现；整理期间发现业务 bug，不自动把成因归于并行开发。

每项改动都应对应实际问题和预期结果。新增产品能力、全库重构、重排目录和重建运行方式不属于每轮固定动作；确有必要时，先说明具体阻塞与所需变化，并核对已有授权。遇到必须由用户决定的范围或破坏性操作，准备可审阅的具体结果再询问，同时继续其他可独立推进的事项。

已暂缓事项沿用项目状态中的决定。范围外发现记录归属和下一动作，不把它们变成本轮维护必须完成的条件。没有发现问题时允许零改动完成。

## 4. 验证并同步

按[选择验证](../acceptance/README.md#选择验证)运行受影响的链路。文档改动核对事实、阅读路径和引用；代码改动按[开发约定](module-development.md#编排)完成对应验证与审查。通过后，仅在新改动、失败或未解疑点需要时扩大或重复验证。

依赖、路径或环境准备发生变化时，按根 AGENTS 的可移植性要求在独立检出中实际重建。核验旧 Git 对象依赖时，可用浅克隆并确认所需旧对象不存在，再执行相关入口；拥有完整历史的克隆可能掩盖这类依赖。缺少外部输入或目标环境时，明确对应未验范围，不记为通过，也不直接判为产品缺陷。

事实改变后同步对应权威文档。当前缺陷、保留现场和下一动作进入[项目状态](../plans/run-state.md)，执行过程与证据按[产物规则](../acceptance/README.md#隔离与产物)保存；不为每次维护新增永久报告或重复待办。事实未变时无需修改状态文档。

## 5. 收尾与交付

按[集成后的清理](module-development.md#集成后的清理)确认成果进入授权基线，再处理本次已完成现场；失败或未集成成果保留接续条件。按[回执](module-development.md#回执)报告检查范围、实际修复、验证结果，以及保留项和原因。

只有范围内必要检查与修复均已通过、文档与实际一致、现场已清理或明确保留原因，才报告全部完成。缺输入或授权导致某项未闭环时，分别报告已完成范围、未完成项及下一动作；已暂缓或范围外事项单列，不以它们阻止其余维护收尾。零改动也须说明检查依据；检查没有发现问题不等于整个产品完成验收。
