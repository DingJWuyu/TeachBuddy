# 按需选择技能

只在任务触发时读对应 SKILL.md。当前会话列出的可用技能及其实际文件是执行依据；旧任务提到的技能不代表本机仍安装，也不自动触发它。

| 当前任务 | 技能 | 使用边界 |
| --- | --- | --- |
| 写供 agent 接续的文档 | writing-for-agents | 先定义读者与触发条件，权威信息一处维护，分层披露 |
| 诊断报错、失败或性能问题 | diagnosing-bugs | 从用户实际路径复现，再缩小原因 |
| 审查分支、PR、WIP 或指定基线以来的 diff | code-review | 按实际 skill 运行 Standards/Spec 两轴，聚合一份报告 |
| 用户要求 test-first / 集成测试 | tdd | 按行为反馈推进；UI 不写单元测试 |
| 设计接口、模块边界、可测试性 | codebase-design | 使用深模块词汇；不要因技能存在就扩为多方案实验 |
| 调研外部 API / 开源能力 | research | 明确问题与一手来源，不把调研当已验证集成 |
| 改领域词汇或稳定架构决策 | domain-modeling | 确有变化才改 CONTEXT / ADR |
| 用户明确要求 Herdr 可视化任务 | herdr | 属于具体派发方式，不替换项目默认模型与授权 |
| 已发生 Git 合并冲突 | resolving-merge-conflicts | 在既有合并权限内处理，不覆盖用户修改 |

其他技能按会话中的触发说明选用。任务明确点名的技能若不可用，说明缺口；不声称执行了不存在的流程。

## 审查和验收不是同一件事

- 实现自验：作者运行必要检查，记 self。
- code-review：检查固定 diff，按实际技能取得两个只读助手的结果。
- 独立流程验收：另一个验收者实际使用候选，记 independent。

根接收聚合结果，不再派同一 diff 的重复审查。普通文档修订、Git 准备和台账更新做必要自检即可。

## 固定受审内容

`code-review` 若使用 `<fixed-point>...HEAD`，未提交和仅暂存的内容不会进入审查。先核对提交权限和实际受审范围，再建立候选；不能把工作区自检写成该 skill 的完整审查。修复后定向复验，只有新增实质问题才再次审查。

skill 不扩大产品范围、外部写入、费用或发布权限。内部模型遵循[执行协议](execution-protocol.md#模型与固定派发)和该任务的明确用户例外；原业务 session 边界由根 AGENTS 保留。
