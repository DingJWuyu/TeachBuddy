# 使用单一静态模块目录与受限模块边界

TeachBuddy 将功能模块视为编译期注册的纵向业务单元：一份权威模块目录保存纯数据公共描述，并分别投影到 Web 与 API 入口；工作台外壳只理解身份、导航、布局资格和封闭类型贡献，模块之间只能通过显式公共端口协作。选择这种方式而不是分别维护前端、后端和共享注册表，或建设运行时插件系统，是为了从结构上消除目录漂移、限制模块权限与数据耦合，同时保留独立演进和故障隔离能力；完整决议记录在 [确定工作台外壳与功能模块的集成契约](https://github.com/DingJWuyu/TeachBuddy/issues/18)。

## Consequences

- 模块 ID 不可复用，注册契约单独版本化；模块公共描述与运行时代码分离。
- 用户页面使用模块声明的顶层业务路径，模块 API 统一挂载到 `/api/modules/<moduleId>/*`。
- 后端注册与页面开放在同一份目录里分开声明：API 装配全部注册模块，Web 只投影已开放的模块，未开放的页面路径不可访问。
- 模块独占自己的数据、迁移与仓储；跨模块依赖声明为必需或可选公共端口，并在构建时校验缺失和循环。
- 契约、依赖或迁移错误阻止构建或启动，单次页面与 API 错误在模块边界内隔离。
- 新贡献类型只在消费者及产品语义明确后加入封闭契约，不预留任意字段或通用插槽。
