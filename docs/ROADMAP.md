# MVP 推进与交付

[返回 README](../README.md) · [产品范围](PRODUCT_SCOPE.md) · [工作台设计](WORKBENCH_DESIGN.md)

本文是唯一执行计划。仓库实际能力由 README 维护，交付范围由 PRODUCT_SCOPE 维护；本文件记录谁在做什么、先后依赖、下一步与完成条件。2026-09-21 起按真实教师任务推进，用户已将范围内的行为、交互、契约和技术决策交给 Agent。

## 推进方法

每轮交付一条可实际使用的教师流程，例如“收下一道题，改编后加入备课，刷新后继续使用”。顺序是：明确行为与结果，约定该流程必需的共享接口，前后端并行实现，当轮连接真实服务并验证。UI/UX 在正式应用中迭代，不再等待全部页面原型和全部接口一次性完成。

开始第一条流程前，只统一会影响多模块的基础含义：账户身份、对象身份、题目/文件/作品与备课的引用、源内容更新和删除、保存失败与重复写入。这些规则必须具体到本轮能实现；未来没有消费者的接口不预设。

每条流程遵循以下步骤：

1. **行为**：协调者在 WORKBENCH_DESIGN 中记录入口、动作、可见结果、保存与返回，给场景稳定编号。覆盖这条流程实际涉及的空数据、等待、失败、重试、离开和恢复。沿用适用的既有场景编号，新增业务场景另用 `WB-` 前缀；引用原型行为时注明来源。
2. **共享约定**：只写双方必须一致的操作、字段、结果和错误语义。前端用具体页面操作检查是否够用，后端用实际存储及失败情形检查是否可实现。内部组件和数据库细节由各自负责方决定。
3. **并行实现**：前端和后端围绕同一场景工作。前端替身直接遵守契约，只用于独立开发与故障验证；真实联调当轮完成，不把替身路径标为交付完成。
4. **真实验证**：协调者按老师的操作路径使用实际页面、文件和数据库，检查关联、刷新恢复、失败反馈及视觉。发现共享含义不一致时先修订同一份契约，再同步两侧。
5. **收尾**：记录运行入口、实际验证结果和剩余缺口；更新本页进度及 README 能力状态，删除本轮被替代的实现与临时产物。未完成的调查和工作保留，防止下一轮丢失上下文。

先独立提出方案，再围绕具体输入输出交叉检查。通常一轮提案、一轮交叉审查即可；有争议时用真实材料或小实验裁决，不因讨论轮数耗尽而把未解决问题算作通过。协调者裁决已授权范围内的取舍，只有范围改变、必要的外部条件或权限才需要回到用户。

## 三个 Agent 的职责

| 角色 | 主要职责 | 默认编辑范围 |
| --- | --- | --- |
| 协调与验收 | 教师行为、契约收敛、关键能力实验、跨模块整合、真实体验和视觉验收、状态维护 | 产品/契约文档、共享定义、集成配置与验收代码 |
| 前端 | 真实页面、编辑与预览、共享右栏、区域滚动、现场恢复、前端契约用例 | `apps/web/`，其中认证页面由独立认证工作线负责 |
| 后端 | 持久数据、文件、转换任务、业务服务、pi 工具接入、后端契约用例 | `apps/api/`，其中认证实现与独立认证工作线协调 |

前后端直接讨论请求、响应和可见结果；协调者维护最终共同约定。根 Agent 同时做能力验证与验收，不只转发消息。OCR、文件转换和 pi 的研究由协调者提前分担，避免全部堆到后端最后处理。

每轮开始指定文件归属和共享文件的唯一编辑者。`packages/shared/`、锁文件、根配置、契约定义和同一测试文件由协调者汇总修改；跨所有权的变更先交给对应负责人。使用受跟踪的 Agent 任务和 Git，不额外搭建任务调度系统，也不自动扩大团队。

## 实施顺序与当前进度

阶段按可验证结果划分。独立的能力实验可以并行进行；开发集中于一条主流程，及时集成后再扩展。每阶段只是完整 MVP 的一部分，不构成缩减交付范围。

| 阶段 | 要得到的结果 | 当前状态 |
| --- | --- | --- |
| 0. 清理基线 | 现状、范围、计划、原型和契约各有归属；旧约束不再误导新开发 | 文档与代码只读审计、文档整理已完成；未改变运行代码 |
| 1. 第一条真实流程 | 自建/粘贴一题，编辑或复制改编，加入备课，刷新后仍能找到；接入外壳和真实存储 | 待开始 |
| 2. 材料进入与成果输出 | 图片/PDF/Word 自动提取和拆题、原稿校对；真实资源预览和更新；三类备课成果的可编辑 Word 与 PDF | 待开始 |
| 3. 数学作品 | 公式、静态图形、动态演示真实制作、修改、导出，备课往返及课堂离线使用 | 待开始 |
| 4. 教学与时间 | 班级记录反馈到备课；连续日期、周重复课及单次调课、事项排序、站内提醒与补记 | 待开始 |
| 5. 完整交付 | Agent 操作全部模块，认证交接与退出、设置/帮助/发布记录、资料导出、误删恢复、备份恢复及部署 | 待开始 |

**下一项具体工作**：阶段 1 的行为与薄契约，先拿真实持久化跑通题目到备课的链路。同时完成以下高不确定性能力的小实验，将实际支持格式、误差、失败恢复和依赖写回对应契约与技术说明：

- 图片/PDF/Word 的数学题提取、拆题、公式和配图保留。
- 可编辑公式的 Word 输出、PDF 排版，以及 PPT/Word 实际内容预览。
- 数学制作工具或 skill、可编辑作品来源、动态作品断网运行。
- pi 的准确包与版本、扩展接口、DeepSeek 适配，并尽早用真实模型完成一次读取和写入已有业务服务。

pi 接入从阶段 1 验证，随各模块逐步开放同一套业务能力，阶段 5 才做全链路收尾。备份、恢复、文件归属和引用规则在建模时考虑，各阶段都有局部恢复检查，不留到交付当天补设计。

若模型凭据、转换工具或部署环境不可用，先核实已有环境并记录具体阻塞，继续不依赖它的工作。未完成的真实调用或文件验证保留为缺口，不能用固定回答或封面替代并宣称 MVP 完成。所需外部信息集中提出，不将普通设计选择交回用户。

## 认证工作线的交接

登录注册原型及契约由另一个 session 负责。当前认证行为已补齐，契约仍停留在旧源版本；见[认证契约](contracts/auth.md)。本轮整理没有修改该契约、认证原型或其用例。

工作台实现需要从认证工作线取得并核对：当前账户身份与昵称、初次进入及恢复登录、会话失效、设置中退出所需的请求与结果。沿用已确认的同源 Cookie 方向，不把旧应用的 Bearer token 当成目标约定。退出入口的 UI 属于工作台；会话撤销和失败语义必须与认证约定一致。

业务服务可以在受控的开发测试环境通过注入账户身份独立实现、验证隔离。这个接缝不进入生产登录路径，不接受浏览器自行声明的账户身份，也不构成认证或跨设备验收通过。认证尚未完成时继续独立业务工作，最终联调仍是完整交付的必要条件。

## 文档与代码归属

- **范围**只在 PRODUCT_SCOPE 维护；**当前实现状态**只在 README 汇总；**执行进度**只在本页维护。撤下的 PROJECT_PLAN 不再作为另一份计划恢复。
- **产品行为**在 WORKBENCH_DESIGN 中逐条细化；共同视觉规则引用设计规则，不复制整套规则。以后验证实现时以这些行为为依据，不以草稿源码反推要求。
- **工作台接口**在实际需要时建立 `docs/contracts/workbench.md` 作为入口，链接唯一 OpenAPI/schema 和对应契约用例。复用认证已确认的公共约定。字段定义只维护一处，API 指南只提供导航，不再手写另一份字段表。
- **旧原型工作流**保留在 `.agents/skills/`，供用户显式选用，也供认证工作线继续使用。本轮工作台开发采用这里的新流程，不以完成全量原型评审或逐条用户确认作为开发门禁；原型历史验收状态保持真实。
- **代码**继续使用 `apps/web`、`apps/api` 和 `packages/shared`。优先复用现有可用底座，不因为目录里有旧代码就整体推倒。逐块替换后移除失效代码和过时测试断言，不为了旧空首页测试恢复错误产品行为。
- **架构**以简单的前后端分离、单一应用后端为起点。现有 React/Vite、Express、SQLite 先保留，文件持久化随能力验证确定；六模块是业务边界，不是六个服务。遵守[已有模块边界决议](adr/0001-use-a-single-static-module-catalog.md)，不从中扩建运行时插件平台；确需修改决议时记录理由。
- **原型证据**留在原位置，标清适用版本。真实 MVP 的行为测试在实现旁维护，复用现有测试工具；只为关键视觉状态和问题保留必要截图，不机械复制每次原型评审的全量截图流程。

使用从 main 创建的开发分支与独立 worktree，每条流程形成可审查的提交，main 保持干净。获得用户许可后及时合回 main 并关闭分支；尚未获得合并许可时，在当前开发分支继续串联已验证流程，不建立多层依赖分支或停止本地工作。自主开发授权不等于自动合并或发布授权。用户可直接在开发分支运行成果。本轮整理分支为 `docs/mvp-delivery-baseline`。

GitHub Issues 继续作为用户明确授权创建的任务记录入口，本轮没有新建 issue；本页提供接续状态，不另建一套任务平台。不重命名整套包、不移动数百份证据，也不为纯整理修改自动生成文件或 CHANGELOG。

## 何时可以称为可交付 MVP

[工作台设计的完整流程](WORKBENCH_DESIGN.md#8-真实-mvp-的行为验证重点)提供业务验收入口，覆盖所有已确认能力。除逐条完成这些流程外，还必须满足：

- 从实际浏览器入口使用真实服务，账户隔离正确，刷新、服务重启及重新登录后内容仍在。电脑完整体验和平板基本操作均实测。
- 真实材料完成提取、修改、复用与输出；Word 中的公式可编辑，Office 预览有实际内容，动态作品在明确记录的支持浏览器中断网可用。
- Agent 实际读取和修改持久内容，页面可找到结果；失败、重复请求及与手动编辑相遇时按约定处理。全过程不会形成一份与手动操作脱节的数据。
- 保存失败不会被显示为成功，草稿和工作现场可恢复；源材料更新、误删恢复和备份还原经过真实检验。
- 独立区域间隙、控件归属、共享右栏、独立滚动、必要反馈和精简文案通过真实任务检查。删除某按钮或说明仍能完成同一任务时，优先删除。
- 提供实际运行地址或经验证的启动方式、环境变量名称、支持格式与环境、备份恢复方法和已知限制。凭据不写入仓库；缺少必要外部条件时如实报告交付阻塞。
- 当前分支的构建、针对新行为的接口/端到端测试通过，状态文档与代码一致。原型截图、旧底座测试、未执行用例不能冒充这些证据。

阶段可以标记“实现及内部验证通过”；只有用户明确验收后才能写“用户验收通过”。已确认范围内仍有未完成能力时，交付状态保留为部分完成，不改名为更小的 MVP。
