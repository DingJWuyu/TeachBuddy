# 代码标准

写代码和做 Standards 审查时读本页。老师应当得到什么结果，由 issue、[分区说明](product/README.md)和用户的指令决定；测试环境和 CI 见 [SETUP](SETUP.md#测试与-ci)。

## 改动范围

- **一个改动目的，对应一个完整的使用结果。** 从用户的输入一路追到输出、保存和重新打开，包括调用者、状态和副作用。单个函数正确，不能证明这个操作完成了。每项行为改动都要有目标依据；范围之外的发现，不混进这次改动。
- **修复要覆盖同一个根因的所有入口。** 去搜共享的读取方、兄弟分支、调用者和相邻状态，按共同的成因修。但也不要把对一种错误的处理扩大到无关的情况。
- **改变了含义，就重查依赖它的地方。** 接口、公式、列表、时序或布局断点变了，要核对调用者、持久化的副本和原有断言，不能只看改动的那几行。
- **读取失败就是未知。** 读取、解析或摘要失败时，不能当成空、没有记录或相等；保留已有的数据和错误信息，并在共享的读取方修复。权限判断所需的输入读不出来时，拒绝放行。
- **用户的内容和配置由用户掌控。** 默认值不能覆盖用户明确做过的选择；同步、替换和恢复只处理本次操作拥有的数据。给用户可编辑的副本时，要核对"用户改了之后再同步或重新打开"的结果。
- **外部格式要有原始依据。** 写其他应用的格式，或者解释模型和工具的输出时，字段的含义、类型和边界要从它的源码、正式文档或真实字节里取，不能凭字段名猜。
- **已经认可的体验要一直能用。** 按分区说明保护已有的功能、已保存的数据和界面体验。分批交付时记下剩余的目标；还没开放的能力保持不开放；不能拿旧测试推翻用户已经确认的行为。

## 方案取舍

- 这是给一个用户用的产品，选直接、完整、内聚的方案，复用成熟的库和已有的公共端口。
- 自己写解析器、渲染器或新的处理层，必须先有具体的缺口。一次性的操作先走最直接的路径，遇到实际的阻碍或重复的需求再加机制。
- 技术取舍优先考虑正确、简单、稳健和长期可维护，不因为实现成本高就降低要求；也不为没有需求的高性能、高并发或高可用增加复杂度。
- 证据已经否定了一个方案时，在授权范围内调整或替换它。

## 验证

- **修 bug 先复现。** 按用户真实的入口、输入、身份和操作做 E2E 复现，记下失败的现象和触发条件，再去定位。真实文件要用真实字节；优先复用已有的固定输入；截断、空值和读取失败按受影响的边界核对。
- **断言检查的是用户或调用者需要的行为。** 新加的回归保护，要在换回旧实现或手动破坏相关保证时，出现有名字的行为失败；编译错误、skip 和测试自身的故障都不算检出。只为值得长期保护的实际缺口新增自动化测试。
- **测试的层次。** UI 不写单元测试，其他单元测试也只在必要时写；资源库用真实浏览器加 HTTP 和数据库的集成测试。浏览器里要核对外观和完整交互，保存后刷新或重新打开读回，输出的文件要实际打开。
- **顺手看界面。** 对受影响的页面，主动检查明显的视觉、交互和焦点问题，以及受影响的主题和尺寸。
- **开发模式和固定构建分开判断。** 改了 Vite、文件监听、挂载或 StrictMode 相关的代码时，启动一个隔离的开发入口，实际操作上传、模块往返、保存和刷新读回，并核对热更新、API 自动重启和登录保持。
- **默认回归要隔离。** 使用隔离的数据、文件、邮件和受控的模型，不能碰用户的实例或私有配置。固定输入来自真实材料，依赖锁定版本；回归里的外部请求用本地替身，真实服务的调用单独作为目标环境专项，并核对授权。
- **测试自己收尾。** 测试启动的服务、子进程、异步任务和临时目录，由这个测试结束或等它们退出。时序测试通过控制延迟来复现，不靠繁忙 Runner 上很紧的墙钟阈值判断对错。
- **红测试和不稳定的测试都是当前的问题。** 先分清是产品、环境、输入还是测试本身的原因，拿到新证据后修根因。不能用"基线也是红的"或"单独跑能过"跳过，也不能降低当前候选已有的保证。
- **作者自己先验。** 在本地定点复现和自验；新增或迁移的回归随所属改动定点实际运行，`--list` 只证明选中了哪些测试，不能代替运行结果。交付前的检查见[执行者](agents/executor.md#checks)。

## 审查和交付

- 审查固定基线和候选，先从 issue 和它的 spec 确认完整的目标；作者的摘要不能缩小审查的目标。
- 沿实际源码核对触发条件、前后行为、状态、失败和兼容语义，同时核对作者声称的证据覆盖范围。
- 做全面核查时，在 issue 或 PR 里列出入口、条件分支和状态转换（包括公共组件的实际使用方），逐项标明通过、批准的差异、失败或未验，不能只复查已经修过的发现。
- 文档更新了，不代表实现正确；测试数量多，不代表范围完整。
- 完成记录要区分作者自验、独立验收和用户反馈，通过、失败、跳过和未验分别写明。缺输入、真实模型或目标设备时，写明哪些没验；不能从局部通过、文件存在或 CI 通过推出整个产品可用。
- 已实现、已集成、已验证要分别确认。严重的审查发现都解决、必要的证据都通过、文档也同步了之后，仍要对照 issue 的验收条件，判断任务是否完成。

## 文档维护

改动了老师看到的行为，就在同一个 PR 里更新 [docs/product](product/README.md) 下对应的分区页。接口语义写在 `apps/api/src/contracts/` 的 OpenAPI 里，代码看不出来的坑写成旁边的注释，它们都随代码一起改。术语和 ADR 按[领域规则](agents/domain.md)。

## 输入和可重建性

- docs 是给人和 agent 读的；产品的构建、运行和业务测试都不把文档当数据。机器契约放 `apps/api/src/contracts`，交换样本放 `apps/api/test/fixtures/contracts`，其余输入放在所属的代码或测试目录；固定版本的兼容输入保留在那个版本的原路径。
- 启动和必要回归用到的脚本和可分发的固定输入都要入库；私有配置提供模板；外部输入写明获取方式和校验值。Git 跟踪的文件和间接依赖，不能依赖个人的绝对路径、旧工作树、只在本机存在的 Git 对象、被忽略的目录或会话记录。
- 依赖和构建产物按入库的清单和脚本重建；私有配置、持久数据和外部工具按 SETUP 准备。测试自己创建隔离目录，产物和清理见 SETUP。skill 的临时工作区，以及不作为读取前提的原始采集路径元数据，可以保留。
- 改变依赖、路径或准备方式时，在一个不复制旧本机目录的独立检出里，按文档安装、配置并实际验证。浅克隆、冷缓存或独立缓存按具体依赖选择；字符串搜索或旧缓存里通过，不能代替重建。缺工具、输入或硬件时明确记下来。
