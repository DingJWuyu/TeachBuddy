## 实现职责与请求边界

这是 D02-D04 已确认分工的实施说明。覆盖表出现一个前端行为或错误原因，不表示要为它创建接口、发送请求，或把前端状态交给后端管理。

| 责任类别 | 现有范围中的例子 | 前端职责 | 后端职责与契约范围 |
| --- | --- | --- | --- |
| 前端独有行为 | 密码显隐、确认密码一致性、空闲时切换表单并保留邮箱、条款链接暂不跳转、已有引导呈现 | 根据上游行为实现和验证；为这些动作本身不发送认证请求 | 不接收确认密码、显隐状态等 UI 状态，不增加对应接口；契约只保留归属与上游引用 |
| 双方都执行的输入规则 | 邮箱空值与格式、昵称非空、密码最短长度、验证码字符形状、条款同意 | 在已验收的触发点按既有顺序本地校验；本地不通过则提示并阻止本次提交或发码请求 | 对实际收到的输入独立执行相同的已确认规则；不依赖前端已经检查。收到不合规请求时按该操作的错误约定拒绝 |
| 后端裁决的账户与身份结果 | 邮箱是否占用、凭据是否正确、验证码绑定及有效性、账户创建、密码变更、会话建立或失效 | 本地校验通过后提交业务操作，按已确认结果呈现；等待和异常恢复仍待相应 G 项 | 根据实际账户、验证码和会话状态裁决；客户端的“已校验”“已发码”等 UI 标记不构成有效性证明 |

**一次提交的边界**：前端先执行该动作已有的本地校验；发现错误时就地反馈，不为了取得同一错误文案调用后端。校验通过后，才向 I01-I05 中对应的业务操作提交一次请求。后端收到请求后独立校验，再按操作条件作出业务裁决。此处描述单次触发的职责，不提前定义连点、重试或在途修改的 G01 行为。

**字段错误码的用途**：D07-D 描述后端确实收到不合规输入时的拒绝响应，以及前端收到该响应后的定位。正常页面中的同类本地错误无需先发送请求，也无需伪造一个 HTTP 422 响应再显示。前端内部是否复用这些标识、两侧是否共享校验代码，由实现者决定；契约只要求已确认规则及可见结果一致。

例如，登录邮箱为空时，页面按 CA02 提示且不调用 I01。若绕过页面直接提交含空邮箱的登录请求，且无其他竞争拒绝条件，后端以 `email-empty` 拒绝。两种路径都使用已有邮箱提示位置，但只有第二种路径存在 HTTP 交换。它们应分别验证，不能只测试页面能拦截，就认为后端已经完成校验。

错误集合按业务操作约束：登录只包含登录字段的错误，发码只包含其输入字段的错误，条款未同意只属于注册，验证码字符形状错误只属于注册确认与密码重置。共享错误 schema 可复用，但不能因此让不相关操作返回其他表单的字段。操作 schema 仍为 partial，完整上下文补齐时再扩展对应字段及结果集合。

前端文案及呈现由已验收行为拥有；后端的 `title`、`detail` 不成为页面文案或分支规则的权威来源。服务器返回错误后用户又编辑或离开页面，旧响应是否仍适用属于 G01，不能由上述职责划分推导。

验证时分别保留三种证据：前端本地拒绝时没有触发认证请求、前端使用替身响应时能定位已定义的字段错误、后端脱离页面时仍拒绝不合规请求。具体片段见[契约用例](auth-cases.md#本地校验与后端拒绝分别验证)。

D04 其余输入边界、D05 的具体交换在相应定义明确后展开。当前 OpenAPI 的类型检查不能替代完整账户输入校验。

**D05-A 操作地址**：已有五项提交操作使用 POST，发送 `application/json` 请求体。地址的权威定义为 OpenAPI，下表为交互索引。I02 在发码操作内完成已验收的邮箱占用判断，不额外要求前端先发一次独立占用查询；重发沿用同一发码操作，其策略待 G02。

| I01 登录 | `/api/auth/login` |

以上地址相对于浏览器页面的同一来源，OpenAPI 使用相对服务器地址 `/`；具体域名未指定。D11 已确认同源访问，内部代理及服务部署由实现者选择。I07 的退出地址另见 D05-B；I06 的调用依据及两者的完整会话交换仍待 G03。

**D07-A 字段错误结构**：每次响应返回一个主要问题，以 `type` 标识原因；有对应请求字段时附 `field`，值使用已确认的交换字段名。在同一责任范围内可判断的已有错误保持上游首错顺序；后端不检查未传输的确认密码。原型把真实后端结果放在前端模拟后产生的跨边界顺序冲突见 G01/G02，不能静默重排后宣称行为完全一致；尚无上游依据的新增错误顺序仍待明确。

`type` 的具体标识使用 `/problems/auth/<错误名>`，由前端按 RFC 9457 相对于该次请求地址解析；它是错误身份，不要求前端再发请求读取说明。已确定的错误包括 `email-already-registered`、D07-C 的六类协议错误、D07-D 的六类字段错误、D07-E 的验证码值不匹配和 D13 的来源防护拒绝，其余枚举随用例定义。

CA13 的邮箱占用拒绝使用 HTTP 409、`Content-Type: application/problem+json`。精确响应与例子由 OpenAPI 的 `EmailAlreadyRegisteredProblem`、`EmailAlreadyRegistered` 拥有；前后端断言见 [CC-CA13-occupied](auth-cases.md#cc-ca13-occupied注册邮箱已占用)。前端按该标识在邮箱字段呈现已验收文案，不以可选的 `title` 判断原因。无对应字段的故障不强行指定字段，其可见处理待 G01。

**D07-B 已知错误的状态码**：

| 情况 | 状态码 | 与行为的关系 |
| --- | --- | --- |
| 请求体不是合法 JSON | 400 | 通信格式错误，不伪装成某个表单字段错误 |
| 来源或固定保护头校验不通过，且没有其他竞争拒绝条件 | 403 | D13 的请求防护拒绝，不关联表单字段；页面呈现待 G01 |
| 请求媒体类型不受支持 | 415 | 上述操作只约定 JSON 请求体 |
| 合法 JSON 中字段缺失、类型错误、违反已定义的输入规则，或包含最终完整 schema 未声明的字段 | 422 | 字段关联仍按 D03 和 D07-A；G06 未决边界不提前加入规则；未知字段按 D08 拒绝 |
| 验证码形状正确但值与对应真实验证码不匹配，且没有其他竞争拒绝条件 | 422 | D07-E，对应 CA22/CA35，后端判断并定位 verificationCode |
| 注册邮箱已占用 | 409 | 对应 S20、CA13 与 CA25 的重复注册拒绝 |

实际 HTTP 状态与响应中出现的 `status` 必须一致。上述通用格式错误如何向最终用户展示仍待 G01；目前确定的是后端可验证的协议分类。错误凭据、过期或失效验证码、限流及各操作成功时的状态与数据随相应行为确定，不从这张表推断。

**D08 严格请求**：后端以最终完整的操作请求 schema 判断未知字段，并以 422 拒绝，不静默忽略，也不做字符串、数字及布尔值之间的隐式转换。当前 Core schema 只拥有已确认的输入片段；在 G02/G03 等上下文补齐前不设置 `additionalProperties: false`，避免把尚待确认的合法上下文误判为未知字段。Core 允许附加属性只是定义未完成，不是正式请求兼容政策。

**D09 成功响应**：有数据的成功响应使用 `application/json`，响应体直接是该操作的结果对象，不另加通用 `data`、`success` 或 `message` 包装。动作已经完成且确实没有返回数据时，使用 204 且没有响应体。操作的成功时点、返回字段和适用状态仍待产品行为；本次没有将任何发码操作直接定义为 204，也没有用空对象代替尚未设计的结果。

以下定义、响应例子及 D10 的开放响应属性规则已写入 OpenAPI。

**D07-C 协议错误标识**：沿用 `/problems/auth/` 前缀，已确认以下错误名。这些是输入协议的拒绝原因，不代替邮箱格式、密码长度、条款同意及验证码有效性等产品规则。

| 单一拒绝原因 | HTTP 状态 | 错误名 | `field` |
| --- | --- | --- | --- |
| 请求体不是合法 JSON | 400 | `malformed-json` | 省略 |
| 请求媒体类型不受支持 | 415 | `unsupported-media-type` | 省略 |
| JSON 根值不是对象，例如数组或 null | 422 | `invalid-request-body` | 省略 |

**D10 响应附加字段**：前端允许已知结果对象增加未使用的字段，并忽略它们；已定义的必填字段、类型及结果身份仍要满足契约。忽略附加字段不等于接受未知 `type`、未知状态或结构不合法的响应，其用户可见恢复规则待 G01。D10 与 D08 请求拒绝未知字段分别适用于不同方向。无字段错误禁止 `field`，因此不能将它作为可忽略的附加字段。

| 动作 | 当前已定义的首错顺序 |
| --- | --- |
| 登录 | 空邮箱 → 邮箱格式 → 短密码 |

| 找回发码 | 空邮箱 → 邮箱格式 |
| 重置提交 | 验证码字符形状 → 短新密码 → 确认新密码不一致 → 验证码不正确 |

具体未决组合：注册时，验证码字符形状正确但真实值错误，同时条款未勾选。当前原型能用固定示例码在前端模拟“验证码不正确”，因此先显示验证码错误；正式前端无法自行判定验证码真实性，而 D02 要求对可本地判断的条款错误先拦截提交。这两项不能直接声称顺序兼容。该组合已归入 G01/G02，需行为工作线补齐并集成；当前用例通过“没有竞争错误”的前置条件限定已定义片段，不擅自宣布组合路径已就绪。

### 已确认：浏览器访问与登录凭据传递

**D11**：正式应用对浏览器提供同一来源的页面与 `/api`，即相同协议、主机及端口。内部前后端可以分开运行，由部署入口转发；本契约不指定部署供应商、进程或代理实现。登录凭据由后端通过 Set-Cookie 响应头设置在带 HttpOnly、Secure 的 Cookie 中，浏览器在相符请求中自动携带；前端脚本不接收或存取该凭据，不写入 localStorage 或 sessionStorage。

浏览器负责保存和附带凭据，前端负责请求同源业务 API 并呈现已约定结果，后端负责验证凭据并管理有效性。前端不从 Cookie 推导账户信息、不尝试读取 Set-Cookie，也不拼接 Authorization: Bearer。需要清除、替换凭据时仍由后端通过响应完成；这只确定执行主体，何时执行及影响范围待 G03。

该约定不决定会话的内部存储技术，也不确定多久失效、记住我、刷新恢复、退出范围或重置后的会话影响。后者继续等待 G03 的已集成行为；仅看到 Cookie 存在也不能代替服务器判断当前身份有效。D12 已确认 Cookie 名称与固定属性，OpenAPI 的 `components.securitySchemes.SessionCookie` 拥有这部分传输定义。具体产生或清除 Cookie 的交换及各操作的完整凭据要求仍待 G03，因此没有添加全局“必须先登录”的 security 要求，不能将方案定义与完整操作要求混为一谈。

核查依据：当前约束没有要求原生移动客户端或第三方跨站 API 调用；手机支持指已验收的响应式浏览器体验。demo 的 Bearer 实现不是新契约兼容条件。[现有部署指南](../DEPLOY_INFINITYFREE_RENDER.md)描述静态站点与 API 异源访问，不能直接用于已确认的新方案。正式实施时必须同步调整部署说明及 README 的正式应用状态；当前仍为契约设计，没有改变 demo 的部署，不将其文档改写成已实施 Cookie 认证。

### 已确认：Cookie 细节与请求防护

以下固定定义已写入 OpenAPI：Cookie 载体见 securitySchemes.SessionCookie，请求头见 components.parameters，403 见 RequestNotAllowed，缓存响应头见 AuthCacheControl。五个已定义操作均引用防护头、403 及缓存约束。

**D12**：Cookie 名称使用 `__Host-teachbuddy_session`，固定属性为 `HttpOnly; Secure; Path=/; SameSite=Lax`，不设置 Domain。前端将其当作不可读取的凭据，Cookie 值的内部编码由后端选择。到期属性待 G03，当前不以省略 Expires/Max-Age 暗示关闭浏览器就退出。浏览器契约验证与本地联调也提供 HTTPS 同源入口，以相同属性验证；不为联调改成前端存令牌或关闭 HttpOnly/Secure。证书和代理工具由实现者选择。

**D13**：当前 I01-I05 的 POST 及后续认证写操作，除已确认的 application/json 外，前端统一添加 `X-TeachBuddy-Request: 1`。后端要求该头取值正确，并校验请求来源：有 Origin 时按完整来源比对部署配置中的公开来源；Origin 缺失时才解析 Referer 的来源进行同样比对。来源不符、Origin 为 null、无法取得或解析来源，或保护头缺失/错误时拒绝；不按字符串前缀或子域后缀放行，不信任客户端自报的转发头作为允许来源。

该固定头不是秘密、登录凭据或一次性验证码。它与浏览器的请求限制及服务器来源校验共同防止其他站点借浏览器发起写操作，不证明请求者已经登录。该浏览器 API 不向其他来源开放 CORS 访问；即便尚未登录，登录、注册发码、找回发码等操作也执行此检查。单独违反上述保护条件、且没有其他竞争错误的请求返回 403、`/problems/auth/request-not-allowed`，不带 field，并且不进入账户、密码、验证码或会话的业务变更。页面提示及恢复归 G01，不能擅自归到密码错误。

Origin、Referer 及 Cookie 由浏览器管理；前端只设置固定保护头及 JSON 请求，后端独立验证。后端直接调用用例需要补上匹配测试公开来源的请求头；浏览器用例则由实际页面发起，以验证真实来源与 Cookie 行为。上述是 HTTP 协议约定，不新增一个取得防护令牌的操作；浏览器来源验证不替代密码或会话验证。

保护头是 HTTP 请求头，不属于 JSON 请求属性，因此不与 D08 的未知请求字段拒绝混用。它只附在原本允许发出的请求上，本地校验失败仍然不发送请求。关闭跨源访问本身不会阻止普通跨站表单抵达服务器，不能省略后端检查；本方案也不替代站内脚本安全措施。来源头被浏览器环境或代理剥离且无法回退时会被拒绝，不能静默放行，该故障的页面呈现继续归 G01。

**D14**：范围内认证 API 的所有成功和失败响应统一返回 `Cache-Control: no-store`，前端不得以 Service Worker 或应用响应缓存代替一次按契约要求发起的新认证请求。当前页面为呈现结果而保留的数据不由此禁止；何时重新检查身份、清理页面或恢复状态仍依 G03。该缓存规则不保证清除旧缓存或浏览器历史画面，不清空 Cookie 或表单状态，不决定会话是否失效，也不影响静态资源缓存。未来会话检查接口的精确结果仍待 G03，定义该接口时沿用此响应缓存约定。

### 已确认：已有退出动作与验证码拒绝

**D05-B**：I07 采用 `POST /api/auth/logout`，已写入 OpenAPI。已验收的 CA07/CA25 有退出动作；这里先确定承载它的方法和地址，沿用 D13/D14 的来源防护及响应缓存要求。退出请求是否有范围字段、只结束哪个会话、重复退出或无有效凭据时怎样响应、何时回到登录及网络失败如何处理，均继续等待 G01/G03。不能从当前原型按钮没有参数就推断请求体为空，也不预先指定 204；OpenAPI 未声明请求体表示尚待定义。

I06 保留为身份确认/恢复的候选交互。当前原型仅保存内存身份，CA09 刷新回登录不构成真实查询或恢复政策；暂不增加自动查询、刷新令牌或心跳操作，等待 G03 明确调用依据后再设计。

**D07-E**：对已有 CA22/CA35 的验证码不正确拒绝，限定为验证码字符形状正确、其他条件满足但值与对应真实验证码不匹配，使用 HTTP 422，type 为 `/problems/auth/verification-code-incorrect`，field 为 `verificationCode`。精确响应由 OpenAPI 的 `VerificationCodeIncorrectProblem` 与 `VerificationCodeIncorrect` 例子拥有，只列入 I03/I05 的结果。前端呈现已有验证码错误文案，真实性由后端裁决。它不同于已确认的 `verification-code-invalid-format`；不把过期、已消费、地址不匹配或限流等未定结果归入此标识。绑定上下文、错误次数、重发及修正后的成功交换仍待 G02，不使用原型固定码定义正式有效值。两侧验证片段见[CC-CA22-CA35-incorrect-code](auth-cases.md#cc-ca22-ca35-incorrect-code验证码值不匹配)。

### 技术依据

技术依据与用户确认分别记录，标准本身不决定未决的产品行为：

- [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-3.4) 定义 HTTP 请求与响应语义。已确认的 D01 不预设邮件投递同步完成。
- [OWASP 输入校验](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html#client-side-vs-server-side-validation) 建议前端提供体验校验、后端独立验证输入；已确认的 D02 采用这一职责分工。
- [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html#section-3.1.4) 区分可供程序处理的错误信息和人类可读说明。D03 确定分工，D07 已选择该标准格式，其项目扩展仍待定义。
- [OpenAPI 3.2.1](https://spec.openapis.org/oas/v3.2.1.html) 提供与实现语言无关的 HTTP 接口描述，支持 YAML 表达；定义文件固定使用这一已发布版本。
- [RFC 8259 数字表示](https://www.rfc-editor.org/rfc/rfc8259.html#section-6) 不允许 JSON 数字的前导零；验证码的字符串表示保留其完整字符。
- [RFC 9110 客户端错误](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5) 定义 400、409、415、422 的语义，D07-B 已确认它们与本项目已知情形的映射。
- [JSON Schema 对象属性](https://json-schema.org/understanding-json-schema/reference/object#additionalproperties) 支持显式限制未声明属性；D08 已确认最终完整请求采用严格字段校验。
- [RFC 9110 的 204](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.5) 表示请求已完成且没有响应内容；D09 已确认将它用于确实不需要返回数据的已完成操作，不预设任何发码操作已完成。
- [MDN Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie#httponly) 说明 HttpOnly 限制脚本访问 Cookie，浏览器仍可在请求中携带它；Secure 限制生产凭据经 HTTPS 传递。D11 已确认该载体，D12 已确认主机限定属性，不把浏览器 Cookie 留存当成会话有效性政策。
- [OWASP 会话管理](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)与[跨站请求伪造防护](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html#employing-custom-request-headers-for-ajaxapi)提供 D13 的技术依据：JSON API 可使用自定义头，再配合来源校验；请求头、适用操作及拒绝规则是本项目已确认的选择，不是标准替用户确定的业务行为。
- [RFC 9111 的 no-store](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2.5)约束 HTTP 缓存存储和复用响应；D14 已确认该响应缓存策略，不把它解释为清除其他客户端状态或撤销会话。
